# Specification coverage and validation

Source of authority: `Phase_1_Food_Delivery.docx`. The companion Markdown was read as context; the original DOCX was extracted directly and compared before implementation.

| DOCX requirement                               | Implementation                                                                           | Validation                                                                                   |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Four roles, account registration/login/profile | Identity module, persistent opaque sessions, public-role allowlist                       | API authorization tests and browser role logins                                              |
| Register and approve restaurants               | Membership-backed kitchen records, admin approval/rejection                              | Registration/approval and membership tests                                                   |
| Menu CRUD, options, availability               | Menu categories, items and validated options; archive preserves history                  | Cross-restaurant write tests and browser menu edits                                          |
| Search/filter/sort restaurant or dish          | PostgreSQL discovery query, cuisine chips, sort/search UI                                | API dish search and browser empty/result states                                              |
| Persistent cart                                | Customer-scoped JSONB lines and optimistic version                                       | Stale-version conflict, mixed-kitchen rejection                                              |
| BR1 availability                               | Revalidation under checkout locks                                                        | Unsellable item and unapproved restaurant checks                                             |
| BR2 authoritative price                        | Server quote/checkout pricing and immutable item snapshots                               | Client price tampering and price-change tests                                                |
| BR3 one seller per order                       | Restaurant enforced at pricing and persisted on order                                    | Mixed-restaurant rejection                                                                   |
| BR4 payment confirmation once                  | Reference/event/transaction uniqueness, locked state update                              | Duplicate signed callbacks, conflicting event identity                                       |
| BR5 state transitions                          | Separate order/payment/delivery lifecycles and history                                   | Wrong-state rejection, successful delivery, failed delivery                                  |
| BR6 idempotency                                | Customer/key uniqueness, fingerprint and advisory lock                                   | Five simultaneous retries return one order; changed payload conflicts                        |
| BR7 ownership                                  | Membership/assignment/owner checks for reads and writes                                  | Cross-restaurant, cross-customer, reassigned-driver tests                                    |
| BR8 audit                                      | Admin changes, menu edits, order changes, assignment, invalid callback events            | Audit assertions and operations UI                                                           |
| Last serving concurrency                       | Integer stock, row locks, atomic reservation/release                                     | Exactly one of two simultaneous requests succeeds, stock never negative                      |
| Provider timeout/crash window                  | Persistent pending reference, idempotent create/query, timeout and worker recovery       | Timeout injection, post-commit restart/recovery simulation                                   |
| Payment expiry and late callback               | Reservation expiry independent of provider availability, refund queue                    | Expiry, late success, no resurrection and simulated refund tests                             |
| Driver assignment and tracking                 | Manual assignment, reassignment invalidation, history, seven-second UI polling           | Complete browser lifecycle and old-driver rejection                                          |
| Reviews/complaints                             | Buyer eligibility, one review, admin moderation/resolution                               | API and browser tests                                                                        |
| Notifications                                  | Transactional outbox with bounded retries and deduplicated inbox                         | Duplicate-worker execution test                                                              |
| Revenue/order/delivery reports                 | Delivered gross value and status counts, restaurant scoping                              | Delivered order/revenue assertion and operations UI                                          |
| Security                                       | Scrypt, DB sessions, CSRF checks, Helmet, Prisma parameterized queries, rate limits      | Invalid login/origin, forbidden role escalation, suspension tests                            |
| Observability                                  | Request IDs, structured latency/error logs, process metrics, reconciliation/outbox views | Read-only load smoke and admin metrics endpoint                                              |
| Recovery                                       | PostgreSQL volume and backup/restore procedure                                           | A backup restore smoke test is described in operations; production RPO/RTO remains undefined |

The three browser scenarios include WCAG A/AA automated checks on discovery and authentication, keyboard Escape dismissal, viewports of 375/768/1024/1440px, and screenshot review. Automated accessibility tests are useful checks, not a claim of exhaustive accessibility certification.

Not implemented as real external services: commercial payment/refund settlement, maps/geocoding/GPS, email/SMS/push, multi-restaurant checkout, advanced complaints/refunds, capacity slots, promotions, legal KYC, payouts, or production backup automation. These are conditional or unresolved in the source and require business/provider decisions. The local app does not claim the preliminary 99.9% availability or production response-time target has been achieved.
