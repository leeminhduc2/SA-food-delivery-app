# Implementation decisions

These are implementation defaults for the preliminary Phase 1 DOCX, not externally approved business policy.

| Topic               | Implemented choice                                           | Reason and consequence                                                                                                                                                                                                                                                                             |
| ------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Architecture        | Modular monolith, PostgreSQL, React web client               | No Redis, broker, or search engine without load evidence. Modules call domain functions for writes to another module's data. Reporting and order-detail projections join across modules.                                                                                                           |
| Currency            | Integer VND                                                  | Avoid floating-point pricing; no multi-currency settlement.                                                                                                                                                                                                                                        |
| Cart                | One restaurant per checkout                                  | Mixed-restaurant requests fail. Multi-restaurant parent/suborders are intentionally excluded because the document makes them conditional.                                                                                                                                                          |
| Menus and extras    | Named menu categories; optional extras with fixed surcharges | Extras are stored as validated JSONB inside their owning menu item; their snapshots are stored on order items. No required modifier groups or minimum/maximum selection rules are specified.                                                                                                       |
| Inventory           | Available serving count per item                             | Checkout locks the restaurant and item rows, reserves servings, and writes all order/payment/history/outbox data in one transaction. Item locks are ordered. Reservation is released once on payment failure, expiry, or eligible cancellation. Prepared or failed-delivery food is not restocked. |
| Stock editing       | Staff sets currently available servings                      | The number excludes reserved servings. A released reservation is added back. This is not a daily capacity calendar.                                                                                                                                                                                |
| Pricing             | Authoritative item/extra prices plus restaurant delivery fee | Client supplies `expectedTotal` only to detect a price change. Server recalculates. A changed total returns `PRICE_CHANGED` and requires confirmation. No promotions/taxes/tips are inferred from the document.                                                                                    |
| Idempotency         | Unique customer/key plus normalized request fingerprint      | Same key and payload return the existing order; changed payload conflicts. A transaction advisory lock serializes concurrent use before the unique constraint. Read results show current order state.                                                                                              |
| Payment window      | 15 minutes, configurable                                     | Stock is reserved until expiry. Worker expires orders even while provider calls fail. Recovery lag depends on worker scheduling and load.                                                                                                                                                          |
| Payment attempts    | One stable reference per order                               | Retry reconciles that reference. A failed checkout requires a new order; multiple payment attempts per order need a provider contract and schema extension.                                                                                                                                        |
| Cancellation        | Customer, owning restaurant, or admin before acceptance      | Pending/confirmed orders can be cancelled with a reason. Confirmed payment enters `REFUND_PENDING`. Later cancellation requests are rejected and can go to support.                                                                                                                                |
| Late payment        | Record success as refund pending; never reopen order         | Reconciliation flag and audit preserve the event. Simulator can complete refunds when its authoritative transaction succeeded. A real provider must confirm its refund result.                                                                                                                     |
| Delivery assignment | Manual admin assignment                                      | Only an active driver can be assigned. Reassignment is possible before pickup; the previous assignment becomes inactive.                                                                                                                                                                           |
| Delivery failure    | Explicit `DELIVERY_FAILED` order state                       | Failure requires a reason and remains visible to operations. No automatic refund, restock, or retry is inferred after pickup.                                                                                                                                                                      |
| Reviews             | One review per delivered order from its customer             | Restaurant-level feedback; no per-item ratings in this first implementation. Moderation hides content without deleting order evidence.                                                                                                                                                             |
| Reporting           | Gross delivered order value, including delivery fee          | Excludes undelivered/cancelled orders. Daily grouping uses order creation date in database UTC. This is not net restaurant payout or financial reconciliation.                                                                                                                                     |
| Notifications       | Durable in-app inbox                                         | Outbox insert commits with the business change; worker uses row locks and unique event IDs. Failed delivery retries up to five times.                                                                                                                                                              |
| Authentication      | Scrypt hashes and random opaque session cookie               | Session hashes/expiry live in PostgreSQL. Cookies are HttpOnly, SameSite Lax, and Secure in production. No JWT secret or session state in app memory.                                                                                                                                              |
| HTTP protection     | Origin allowlist plus required custom header for mutations   | HMAC callbacks have separate verification. Rate limits are per process; use an ingress/shared limiter for a multi-instance deployment.                                                                                                                                                             |

## Transaction ordering

Checkout obtains a customer/key advisory lock, a shared restaurant lock, then menu-item locks in item-ID order. Order lifecycle changes lock the order before payment/delivery rows. Cancellation and payment failure invoke the catalog stock-release contract in item-ID order. State history includes a database sequence so events within the same transaction retain their insertion order.

Provider calls happen after commit. `ensurePayment` is safe to retry because the simulator uses a unique reference. Calls are time-bounded; an unresolved result remains durable. The reconciliation worker rotates due records through a persisted `next_reconcile_at` timestamp. Expired references are queried for seven days; authenticated late callbacks remain supported after that query window. A real provider must support reference lookup/idempotency or the adapter needs a stronger uncertainty protocol.

## Decisions still needed for deployment

Select the actual payment and notification providers; agree on refund/cancellation policy, settlement, fees, service area and address validation, data retention, expected traffic, availability measurement, RPO/RTO, backups, and operational escalation. The code implements a demonstrable application, not evidence that these business and infrastructure questions have been resolved.
